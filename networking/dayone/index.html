✎ Day One — What is a Socket?

Date: my first day in the Beej's Guide. I wanted to understand what actually happens when two programs talk over a network, so I started at the very bottom: the socket.

⚑ Chapter 2 — Concepts to Remember

What is a Socket?

A socket is an endpoint used by programs to communicate with other programs. That's the whole idea — two programs each hold one end of the pipe and send data through it.

A file descriptor is an integer that identifies an open resource, such as a file, a pipe, or a socket. In Unix-land everything is a file, so a socket is just another thing you refer to by a number.

The Basic Calls

  • socket() creates a socket and returns its file descriptor.
  • send() / recv() send and receive data through a socket.
  • read() / write() can also work with many sockets.

Reminder to self: creating a socket does not automatically connect it to another program. It's just a handle until you do something with it.

Types of Sockets

There are internet sockets (network communication) and Unix domain sockets (local inter-process communication). But the two I need to remember are:

Stream Sockets — SOCK_STREAM

Reliable two-way connected communication streams. If you output two items in the order “1, 2” they arrive in the order “1, 2” — and error-free. The HTTP protocol uses stream sockets, and stream sockets use Transmission Control Protocol (TCP).

Datagram Sockets — SOCK_DGRAM

Connectionless and less reliable. If you send a datagram, it may arrive. It may arrive out of order. But if it arrives, the data within the packet is error-free. The advantage is that they don't need to maintain an open connection like stream sockets do. Datagram sockets use User Datagram Protocol (UDP).

Encapsulation

How a packet travels down the stack:

A packet is born, then wrapped (“encapsulated”) in a header (and rarely a footer) by the first protocol (say TFTP). The whole thing — TFTP header included — is encapsulated again by the next protocol (UDP), then again by the next (IP), then again by the final protocol on the physical layer (say Ethernet).

When another computer receives it, the hardware strips the Ethernet header, the kernel strips the IP and UDP headers, the TFTP program strips the TFTP header, and it finally has the data.

The Layered Network Model

The layered model divides network functions into layers, so each layer handles a specific task. This lets socket programs work independently of the underlying hardware and transmission method. The standard OSI model has 7 layers:

  1. Application
  2. Presentation
  3. Session
  4. Transport
  5. Network
  6. Data Link
  7. Physical

✎ Chapter 3 — Structs and Data

The socket descriptor is just a regular int. To use it you fill in a struct sockaddr_in and hand it to the kernel:

  • sin_family — set to AF_INET (host byte order).
  • sin_port — the port, converted with htons() to network byte order.
  • sin_addr — the address, e.g. via inet_addr().
  • sin_zero — padding, zeroed out with memset().

Byte order matters: htons() = host to network, short. Local machines and the network don't always agree on which end of a number is first.

▶ My First Socket Program (ch4/main.c)

Setting up an internet socket and binding it to a port. No error checking yet — that's a job for a later day!

Files/NotesCode/ch4/main.c
#include <string.h>
#include <sys/types.h>
#include <sys/socket.h>
#include <netinet/in.h>

#define MYPORT 3490

int main(void)
{
  int sockfd;
  struct sockaddr_in my_addr;

  sockfd = socket(AF_INET ,SOCK_STREAM , 0);

  my_addr.sin_family = AF_INET; // host byte order
  my_addr.sin_port = htons(MYPORT); // short, network byte order
  my_addr.sin_addr.s_addr = inet_addr("10.12.110.57");
  memset(&(my_addr.sin_zero), ’\0’, 8); // zero the rest of the struct
  // don’t forget your error checking for bind():
  bind(sockfd, (struct sockaddr *)&my_addr, sizeof(struct sockaddr));

}
